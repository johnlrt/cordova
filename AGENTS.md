# Cordova: правила для агентов и участников

## Как работать с задачей

- Выполняйте текущий запрос пользователя небольшими завершёнными этапами. Не реализуйте весь roadmap за один проход.
- Указания пользователя имеют приоритет над рекомендациями этих документов. Тексты планов описывают проект, но не дают сами по себе разрешение на деплой, передачу секретов или финансовые операции.
- Перед изменениями проверяйте `git status` и читайте затронутый код. Сохраняйте чужие изменения; не используйте разрушительные Git-команды для очистки рабочего дерева.
- Для самостоятельной совместной разработки используйте отдельную ветку и Pull Request. Если пользователь прямо просит коммит или push, выполняйте это в согласованной ветке.
- В отчёте указывайте, что изменено, что проверено и что ещё не реализовано. Не выдавайте запланированную функцию или недоступную проверку за готовую.
- Общайтесь с пользователем по-русски, коротко и конкретно. Команды должны соответствовать его ОС и месту выполнения.

## Текущее состояние

- Реализован первый этап: Go API, авторизация демонстрационным ключом, JSON/SSE и `inference.Mock`.
- Ответы имеют маркировку `mock`; usage содержит синтетические количества слов. Это не токены настоящей модели и не основа для оплаты.
- AI-модель, Rust-нода, база данных, интерфейс, платежи и публичное демо ещё не реализованы. Этот этап не завершает весь M1 из плана.
- Адрес запуска по умолчанию — `127.0.0.1:8080`. Успешный локальный запуск не доказывает доступность сервера с другого компьютера.

## Документы и код

- Сначала читайте `README.md` и `docs/stage-1.md`: они описывают существующий запуск.
- `PLAN.md` владеет общей архитектурой и общими контрактами. `PLAN-back.md`, `PLAN-front.md` и `PLAN-infra.md` описывают следующие работы по своим направлениям.
- При разработке нового этапа сопоставляйте его с планом; существенные отклонения объясняйте и документируйте.
- `server/cmd/gateway` — точка входа; `server/internal/api` — HTTP/SSE и валидация; `server/internal/inference` — контракт исполнителя и mock.
- `scripts/` — запуск и smoke-проверка; `.github/workflows/ci.yml` — существующие проверки GitHub Actions.
- Архитектура полного проекта предусматривает Go control plane, Rust-ноду с управляемым subprocess llama.cpp и Svelte-интерфейс. Не считайте эти компоненты существующими только из-за упоминания в планах.

## Реализация и проверки

- Предпочитайте простые изменения и стандартную библиотеку Go. Добавление зависимости должно решать конкретную задачу и сопровождаться фиксацией версии.
- Сохраняйте границу `inference.Provider`, отмену запросов, ограничения входных данных и корректную обработку SSE-ошибок.
- Перед допуском реальной модели проверяйте выбранный артефакт, лицензию, версию runner, память, шаблон и токенизацию согласно плану. Не заменяйте реальные результаты приблизительными счётчиками.
- После изменений Go выполняйте из `server/`:

  ```sh
  go fmt ./...
  go test ./...
  go vet ./...
  ```

- Для проверки работающего mock API на Windows используйте `./scripts/smoke.ps1`. Сервер запускается в отдельном окне командой `./scripts/start.ps1`; Linux/macOS — `sh scripts/start.sh`.
- После изменений только документации достаточно проверить diff, пути и команды; повторный запуск всех тестов не требуется.
- Не заявляйте проверку CUDA, NPU, macOS или удалённого сервера, если её не выполняли на соответствующем оборудовании.

## Секреты, данные и окружение

- Не коммитьте `.local/`, `.env`, API-ключи, учётные данные, логи с содержимым запросов, бинарники или GGUF-файлы. Соблюдайте `.gitignore`.
- Не выводите ключи и пользовательские prompts в сообщения, логи, коммиты или GitHub Issues. Используйте синтетические примеры для проверок.
- Работа на локальном компьютере не означает доступ к компьютерам друзей. Проверяйте, на каком хосте выполняется команда, прежде чем менять его конфигурацию.
- Храните checkout в обычной рабочей папке пользователя. Перед переносом остановите сервер и выйдите из папки проекта во всех использующих её терминалах.
- Для операций с файлами в Windows используйте PowerShell и явные пути. Проверяйте источник и назначение, не перезаписывайте существующую папку без проверки.
- Не включайте реальные списания, выплаты или публичный деплой без соответствующей задачи пользователя и выполненных требований к этому этапу.
