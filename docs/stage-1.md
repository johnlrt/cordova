# Этап 1 — проверяемый API-каркас

Дата: 2026-10-09. Scope: одна небольшая часть, по просьбе команды. Реализация не требует MacBook и не использует GPU.

## Граница этапа

Готовы Go gateway, in-process mock executor, ключ из локального файла/окружения, каталог, buffered/SSE Chat Completions, проверка JSON, ограничения и тесты. Синтетический исполнитель не является сетевой Rust-нодой. Его назначение — проверить формат ответов и lifecycle клиента.

Аккаунты, Svelte, Redis, Kafka, WebSocket-сессии нод, настоящий tokenizer, модель и XMR остаются в очереди. Здесь нет сохраняемого состояния или финансовых обязательств. Original PLAN.md сохранён как roadmap; этот документ явно определяет текущий меньший этап.

## Настройки

| Параметр | Значение |
| --- | --- |
| `-listen` | `127.0.0.1:8080` по умолчанию |
| `-key-file` | `.local/api-key.txt` относительно текущей директории |
| `CORDOVA_API_KEY` | Необязательный ключ из окружения; имеет приоритет над файлом |
| `-init-key` | Создать ключ и выйти; существующий файл не перезаписывается |
| `-version` | Показать этап и mock-режим |

Ключ должен иметь минимум 32 символа. Генератор создаёт 256 случайных бит. Ключ не печатается сервером; `.local/` исключён из Git и release bundles. На Windows доступ к файлу зависит от ACL пользовательской папки; Unix creation mode — 0600.

После изменения исходников нужно пересобрать существующий бинарник: start-скрипты используют уже имеющийся `bin/cordova-gateway`, чтобы запуск bundle не требовал Go.

```powershell
cd server
go build -trimpath -o ../bin/cordova-gateway.exe ./cmd/gateway
cd ..
./bin/cordova-gateway.exe -init-key
./bin/cordova-gateway.exe
```

`-init-key` нужен только один раз. Если ключ уже существует, сразу запускайте сервер. В Linux/macOS убрать расширение `.exe`.

## Реализованный контракт

`/healthz` доступен без ключа. Оба `/v1/` endpoint требуют `Authorization: Bearer <demo key>`. Идентификатор модели — `cordova-chat-small-v1`. Каталог возвращает нулевые тестовые ставки; `availability: ready` означает готовность mock executor.

Запрос:

```json
{
  "model": "cordova-chat-small-v1",
  "messages": [{"role": "user", "content": "Hello"}],
  "max_tokens": 128,
  "stream": true,
  "stream_options": {"include_usage": true}
}
```

Поддерживается только этот небольшой набор полей. `max_tokens` — целое 1–2048, по умолчанию 512; в mock-режиме ограничивает синтетические единицы-слова. `stream` по умолчанию false. `stream_options` используется только при streaming. В messages разрешены system/user/assistant, текстовое content и минимум один user turn. Пустая строка content допустима; отсутствие, null и массив — ошибка.

Неизвестные поля, включая temperature/top_p/tools, возвращают 400 `unsupported_parameter`. Это явно неполная совместимость с Chat Completions. Неизвестная модель возвращает 404. `Idempotency-Key` пока отвергается: хранилища для дедупликации ещё нет.

Успешный SSE: role → content → finish → optional usage → `[DONE]`. При ошибке после начала потока отправляется error и соединение завершается без `[DONE]`; HTTP-код уже остаётся 200. Ошибки не включают raw exceptions, ключи или входной текст. `X-Request-ID` — UUIDv4.

Лимиты: body 1 MiB, 128 сообщений, 256 KiB на сообщение, 1 MiB output, 1 одновременно выполняемый запрос, 120 секунд на исполнение, 5 секунд на запись части SSE. Второй запрос при занятом исполнителе получает 429 с `Retry-After: 2`; очереди пока нет. Нет пользовательских rate limits, межаккаунтной авторизации и TLS; поэтому этап по умолчанию привязан к loopback. Для сетевого демо следующего этапа нужны HTTPS и ограничения доступа.

У mock executor нет настоящего tokenizer. Его `usage` и `max_tokens` служат только transport fixtures. Тесты подтверждают формат и поведение потока, но не доказывают tokenizer parity, работу GPU, privacy чужой ноды или корректность денег.

## Структура для изменений

- `server/cmd/gateway` — запуск, ключ, graceful shutdown.
- `server/internal/api` — HTTP, validation, buffered/SSE formatting.
- `server/internal/inference` — контракт исполнителя и временный mock.
- `scripts` — запуск и проверка.
- `.github/workflows/ci.yml` — format, vet, race tests и build на Linux.

Зависимостей Go кроме стандартной библиотеки нет. Версия компилятора зафиксирована в go.mod. Сторонние библиотеки WebSocket/Redis добавляются только на соответствующих следующих этапах. GitHub Actions закреплены по commit SHA; release workflow и промышленная инфраструктура ещё не реализованы.

## Проверки

```sh
cd server
go test -count=1 ./...
go vet ./...
go build ./cmd/gateway
```

На Linux с C toolchain также `go test -race ./...`; CI выполняет этот вариант. Локальные Windows tests без race не заменяют подтверждение GitHub CI.

Проверяются авторизация, невалидные и повторяющиеся поля JSON, лимиты, совпадение buffered и SSE-текста, финальный usage, прекращение успеха после сбоя, настоящая HTTP flush-передача, отмена исполнителя при отключении клиента и предел конкурентности.
